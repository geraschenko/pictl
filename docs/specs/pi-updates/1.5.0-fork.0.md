# Bundled pi update: 0.87.1-fork.0 → 1.5.0-fork.0

Status: audit written; awaiting approval. Nothing beyond the dependency bump is implemented.

# SPEC

Proposed; not yet approved. See IMPLEMENTATION IDEAS for the evidence and the open decisions.

Migrate the bundled fork from 0.87.1-fork.0 to 1.5.0-fork.0, keeping the caret range policy (`^1.5.0-fork.0`).

Proposed success criteria:

- Type, lint, formatting, test, and build checks pass; the API report is reviewed.
- Comments and docs that mirror pi's behavior match 1.5.0: the revival comment in `daemon.ts`, and the RPC image section of `docs/pi-modifications.md`.
- Regression tests pin the new `steer`/`follow-up` output (`{"disposition": …}`).
- The open decisions below are settled, and the approved ones are implemented with tests.
- An isolated, provider-free process check covers: spawn, socket readiness, subscribe seed vs `get-state`, prompt dispositions, steer/follow-up output, the fullscreen TUI under `attach`'s screen snapshot, shutdown, and persisted-session revival.

Non-goals: optional refactors, fork changes, credential access, paid provider calls, and modifying existing agents.

## Implementation-Time Decisions

- **Out-of-band stream cutoff for D1.** A handled prompt may be followed by no events at all, so a handler-side "stop at the next event" flag would hang until the timeout. Instead, `runStream` takes an optional `cutoffSignal: AbortSignal`. On abort, the stream ends as `done` once the events already received are handled. `driver.ts` is canonical for the clauctl sync, so clauctl picks up the optional parameter on its next sync; existing callers are unaffected.
- **`run_aborted`, not `agent_settled`, as the control kind.** The other kinds are named after their event and fire on every occurrence. This record fires only for an aborted settle, so it is named after what it reports.

### O1 and smoke harness

- O1: `npm run check` now also runs `tsc -p extensions`, which checks `navigate-tree.ts` and its test (`--listFilesOnly`). `npm run lint` covers `extensions`. `npm test` runs 232 tests (216 + 16 from the extension).

- The `/tmp` probe's intermittent "no modes or snapshot" was a probe bug. It wrapped `encodeHello` (already a full frame) in `encodeFrame`; the server's `decodeHello` threw, and the client was dropped unless the snapshot was written first. A `[daemon] pi exited with code 0` line seen while debugging came from the debug cleanup killing pi. With the probe fixed, the harness passed 3/3.
- **Finding (D2):** pi's fullscreen enables `?1000h ?1002h ?1004h ?1006h`. The attach snapshot carries `?1049h ?1002h ?1004h ?2004h ?25l` but not `?1006h`, because `@xterm/addon-serialize` serializes the mouse tracking mode (1002 subsumes 1000) but has no case for the SGR mouse encoding. `attach.ts` renders the snapshot as-is, so a fresh attach gets button-motion reporting in the default X10 encoding until pi re-emits its modes. Whether pi misparses those reports was not verified. This gap is new with this update: 0.87.1's default regular TUI enabled no mouse modes.
- SGR options. No released or beta `@xterm/addon-serialize` emits the mouse encoding (checked 0.14.0 and 0.15.0-beta.330). Public `IModes` has no encoding field, even in `@xterm/headless` 6.0.0. xterm tracks the encoding privately as `_core._coreMouseService.activeEncoding` (`DEFAULT`/`SGR`/`SGR_PIXELS`) in 5.5 and 6.0.
  - (1) Read that field in `PtyScreen.serializeScreen`, like `isCursorHidden`, and append the set sequence. The keeper is a `pty-screen` test asserting that `?1006h` survives the snapshot.
  - (2) Track 1005/1006/1015/1016 with public `terminal.parser.registerCsiHandler` hooks; this duplicates xterm's state machine.
  - (3) Propose a mouse-encoding field in xterm.js `IModes` and support in the serialize addon.
  - Recommended: (1), with (3) upstream.
- `encodeHello` now has a doc comment saying it returns a complete frame. Following the TDC on `smoke.sh`, its single-letter names were replaced with role names (`state_dir`, `agent_id`, a `pictl` function, …), as were the probe's (`snapshotDeadline`, `frameDecoder`, …). The harness passed again.

### SGR mouse encoding and snapshot pins

- The user chose (1) plus (3). `PtyScreen.serializeScreen` appends `mouseEncodingSequence(terminal)`, which reads `_core.coreMouseService.activeEncoding` (`SGR` → `?1006h`, `SGR_PIXELS` → `?1016h`; otherwise nothing), with constants in `ansi.ts`. With real pi under fullscreen, the smoke snapshot now carries `?1006h`.
- `pty-screen.test.ts` pins both serialize-addon gaps ("the serialize addon omits cursor visibility", "… omits the mouse encoding"). When an xterm update fills a gap, its test fails and the matching workaround can go. Keeper tests check that snapshots reproduce the cursor visibility and the encoding the process left. Mutating either reader to its fallback fails them.
- The newest addon beta (0.15.0-beta.330) emits `?25l` itself but still lacks the encoding. We are staying on stable.
- Following the review TDCs: `docs/pi-modifications.md` no longer mentions RPC image validation; the fact pictl relies on moved to a doc comment on `imagesFromFlags`. The encoder/decoder framing convention is stated once in the `tty-protocol.ts` header rather than on `encodeHello`.
